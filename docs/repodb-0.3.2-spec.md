# RepoDB 0.3.2 — native refresh throughput and CLI change locality

Status: **proposed, implementation blocked**. This is the new 0.3.2 specification, not a revision of the historical [pre-spec](repodb-0.3.2-pre-spec.md). The separately recorded v0.3.1 release-gate waiver does not waive the mandatory 0.3.2 baseline. No implementation may start until a completed, pinned v0.3.1 release build has been measured with the real, unmodified embedder path; comparable conditions, reviewed task labels and numeric criteria have been agreed; the evidence has been reviewed; and the dedicated baseline ticket has closed. Record the baseline and raw evidence in a separate durable repository artifact, not in this spec. No numeric performance or quality pass is claimed here.

## Problem Statement

Native Git refresh parses independent source blobs with Semgrep serially. An isolated test suggests bounded parallel parsing can reduce parser-stage time, but has not shown a full-refresh gain with embedding and SQLite writes in the loop. Users should not have to trade search quality or dependable indexing for an unverified speedup. Separately, the single CLI dispatcher interleaves global argument handling with every command's parsing, orchestration and presentation; it is difficult for humans to navigate or change safely. The historical pre-spec also proposed an embedding redesign and a database binary split, but those are separate, deferred investigations.

## Solution

Measure a reproducible before baseline, then extract command-specific CLI flows into focused modules without changing their user-visible behavior. Verify the refactor-only build before introducing bounded parallel Semgrep parsing for **native Git refresh**. Use a runtime worker default of `max(1, floor(available_parallelism / 2))`, with a positive CLI/config override. Keep one SQLite writer, bounded queues and result buffers, stable source order keys and deterministic indexed-unit identities. Retry transient parser execution failures once, then fall back per blob; preserve the previous usable index on overall refresh failure. Compare the final candidate with the pinned v0.3.1 baseline under pre-agreed quality and throughput criteria. A full-refresh gain on pinned RepoDB history, with non-regression on the combined language workload and repeat refreshes, is required before claiming success.

## User Stories

1. As a repository maintainer, I want fresh native-history indexing to finish sooner, so that large histories are searchable sooner.
2. As a repository maintainer, I want the speedup measured across the entire refresh, so that parser-only timing is not mistaken for user-visible improvement.
3. As a user, I want exact search to keep finding the same matching content, so that a faster refresh does not omit results.
4. As a user, I want embedding search quality to meet a reviewed floor, so that speed cannot hide lost relevance.
5. As a user, I want source references to remain accurate, so that results still lead me to the correct commit, path and location.
6. As a user, I want the same inputs and parser outcomes to produce stable indexed units, so that worker timing does not change references or tie ordering.
7. As a user, I want every embedding associated with its correct indexed unit, so that parallel parsing cannot silently corrupt semantic results.
8. As a user, I want an individual parser crash or timeout to be retried once and then handled by fallback segmentation, so that one difficult blob does not prevent the rest from being indexed.
9. As a user, I want the previous usable index preserved when a refresh fails or expires, so that searches continue to work.
10. As a user, I want an unchanged refresh to remain quick, so that parallel setup does not penalize the common no-change case.
11. As a user, I want a safe worker default based on parallelism available to the process, so that the software does not assume a particular machine size.
12. As a user, I want to lower or raise the Semgrep worker count with a CLI flag, so that I can adapt a one-off refresh to my machine.
13. As a user, I want to set a persistent worker count in config, so that repeated refreshes use my chosen level without an environment variable.
14. As a user, I want CLI values to override config and invalid counts to be rejected, so that the selected worker policy is predictable.
15. As a user, I want bounded queued work and captured output, so that a slow blob cannot cause unbounded RepoDB buffering.
16. As a user, I want my configured external embedding command and existing indexes to remain supported, so that this release does not silently change model identity or where my text is processed.
17. As a user of imported sources, I want their refresh and search behavior unchanged, so that native-history parallelism does not break imports.
18. As a user, I want search, import, status, refresh and other CLI arguments, text/JSON output, errors and exit status unchanged after the readability refactor, so that existing scripts keep working.
19. As a maintainer, I want each CLI command's behavior easy to find in one module, so that I can change one command without navigating a giant dispatcher.
20. As a maintainer, I want the v0.3.1 comparison and task labels reproducible, so that an improvement claim can be independently checked.
21. As a maintainer, I want the whole refresh process tree's peak memory reported, so that an unexpected resource problem is visible even when no memory threshold is imposed.
22. As a maintainer, I want inconclusive timing results treated as inconclusive, so that noise is not reported as a speedup.
23. As a maintainer, I want the changed CLI evaluated separately before parser parallelism, so that an accidental refactor regression is attributable.
24. As a maintainer, I want the combined 26-language workload tested as one corpus, so that parsing and references across languages remain covered in an end-to-end refresh.

## Implementation Decisions

- **Gate and sequence.** Create a dedicated 0.3.2 baseline ticket first and make every 0.3.2 implementation ticket natively blocked by it where supported. Research and planning may continue, but no implementation begins before the baseline evidence and numeric criteria are reviewed and the ticket closes. Then implement the CLI extraction, check the refactor-only candidate, and only then implement native-history Semgrep parallelism. Keep intermediate results distinct from the final release comparison.
- **Fixed comparison.** Build from the completed pinned v0.3.1 release source and use the same pinned, real generator revision and model artifacts for the before build and candidate; do not use stub vectors, a logging wrapper, or an uncommitted embedder. Pin all tool versions, source histories, task definitions, configuration and commands. A local checkout currently lacks a v0.3.1 tag; resolve the exact released source/build provenance at the gate rather than substituting a candidate build.
- **CLI seam.** Keep one executable. The top-level dispatcher owns global options, database selection and command routing. Each command's module owns its own argument parsing, backend orchestration and presentation behind a small command entry point receiving only its arguments and selected database path. Commands acquire other dependencies as needed. Do not open a write-capable database for commands that do not need one or introduce a shared context containing every dependency. Preserve all existing CLI, JSON, error and exit-status contracts. Judge success by navigability and behavior, not mandatory reductions in soft complexity scores.
- **Parser concurrency.** Only native Git history refresh gets bounded parallel parsing in 0.3.2. Imported-source refresh stays on its existing path. The default is `max(1, floor(available_parallelism / 2))`, using logical parallelism visible to the process at runtime. Provide a strictly positive CLI override and persistent config value; the CLI wins if both are supplied. No environment-variable override for this setting. The [accepted Semgrep default ADR](adr/0001-default-semgrep-parallelism.md) records the deliberate heuristic: do not require cross-architecture tuning before implementation, but revise it if later evidence demonstrates harm.
- **Stable identities and single writer.** Assign each blob a stable order key before concurrent parsing. Once per-blob unit counts are known, derive deterministic indexed-unit IDs without depending on worker completion order. Carry stable temporary blob/unit keys through parsing and embedding, and map each result to its final ID. Workers may complete out of order, but source anchors, embedding association, tie ordering and SQLite's single-writer atomic publication must remain stable for the same parser outcomes. Keep both queued inputs and completed-but-unpublished results bounded; reserve progress for the earliest missing blob and its retry so backpressure cannot deadlock. Do not assume unit counts before segmentation.
- **Failure and cancellation.** Retry a timeout, crash or failed parser launch once via the bounded work queue. Do not retry a successful process response rejected for invalid or unsupported AST. After a failed retry, use the existing per-blob fallback segmentation. Retain per-invocation output capture and timeout limits; retries remain subject to the existing overall refresh deadline. An overall deadline or cancellation aborts and rolls back the refresh rather than treating unfinished blobs as parser failures. Keep the current one-hour default deadline and its existing override. The same parser outcomes must produce the same index regardless of scheduling; a genuine success-versus-fallback difference is a different segmentation outcome and should be visible in verification.
- **Resource scope.** Do not add a per-worker RSS cap, process-tree memory cap, or numeric memory release ceiling. The existing retained-preparation accounting budget is not a cap on process-tree RSS. Do not undertake a separate study or management of Semgrep's own memory use. Keep RepoDB queues, input/result buffers and captured process output bounded; report whole-tree peak memory to spot an unexpected increase and investigate one if observed.
- **Unchanged embedding contract.** Keep the current embedding path, configured external commands and existing model identities; no automatic migration, model port, IPC redesign or implicit artifact download. Use the same model artifacts on both benchmark builds.
- **Other candidates.** Imported-source search profiling is optional and not a gate; no imported-source search rewrite, CLI-related binary split, refresh state-machine restructuring, worktree mapping refactor or ranking refactor is authorized by this spec. No schema migration is required solely for the CLI extraction; any necessary staging changes for parallel parsing must preserve durable schema and public search behavior unless separately reviewed.

## Testing Decisions

- Prefer tests at the existing public CLI seam: run real `init`, `refresh`, `search` and related commands against pinned Git repositories and fresh databases. Assert user-visible output, indexed-unit/source-reference behavior, error and exit status; avoid tests coupled to private worker scheduling or file layout. Supplement with focused parser-failure fixtures and bounded-queue tests where end-to-end tests cannot force a specific race. Existing CLI integration tests and the combined real Semgrep language corpus are prior art.
- **Separate baseline artifact.** Before any implementation, record exact source/build/model/tool versions, generator revision, full Git history/ref pins, corpus generator and resulting commit, environment, cache procedure, commands, raw outputs, search labels, provenance and review decision in a durable baseline file. Do not treat the older instrumented comparison, smoke timings or stub embedder runs as this baseline. Record unavailable metrics explicitly. Set and review numeric improvement/non-regression and quality/reference floors, repeat count and variation rule, and comparable conditions *before* implementation.
- **Performance workloads.** Use the fixed reachable history anchored at the peeled `v0.3.0` RepoDB commit (`f7cc6bc5451204c5696f1bbef7e5575772820f47`) for the required full fresh-refresh improvement. Derive a larger reproducible Git history containing **all 26 existing language fixtures together**, pin its generator, inputs, resulting commit and history, and require full-refresh non-regression on it. Measure repeat/no-change refreshes on both and require non-regression. Use controlled warm-cache conditions, identical warm-up and alternating before/candidate run order; cold-cache measurements are informational if available. Pre-agree repeat count and comparison rule: an inconclusive gain does not pass. Report parser-stage timing to explain full-run results, not substitute for them.
- **Search and references.** Review source-grounded task labels and language coverage before setting quality floors. Test exact correctness, embedding search relevance and source-reference accuracy on the pinned RepoDB corpus. On the scaled combined language corpus, test exact matches and references across languages and add reviewed semantic tasks wherever expected results can be justified; do not label baseline rankings as ground truth. Protect against ranking or reference regression, including ties and identical-content blobs. Preserve the same model identity and external-command behavior across both builds.
- **Resource and failure checks.** Record full-refresh/query wall time, peak memory for RepoDB plus Semgrep and embedding descendants, database bytes, embedding work where measurable without modifying execution, and repeat variation. Report unexpected memory increases for investigation without treating memory as a numeric pass/fail gate. Exercise default, single-worker and positive overridden counts in representative full refreshes, invalid override rejection, bounded queues and output capture, deterministic IDs and vector associations, parser crash/timeout/invalid output, one retry followed by fallback, early-blob retry with later blobs completing, global deadline rollback, and previous-index usability. Do not require a constrained/SMT/heterogeneous-host scaling matrix.
- **CLI-only checkpoint.** After extraction and before parallelism, rerun CLI contracts and the baseline suite. Check each command's arguments, error text, JSON/text formatting and exit status, plus index/search behavior. Treat any difference as a refactor regression rather than attributing it to parser changes.
- **Final decision.** Rerun the same pinned suite against the final candidate. Require the pre-agreed full-refresh gain on RepoDB history, combined-language and repeat-refresh non-regression, and quality/reference floors. Fail the gate on missing or incomparable evidence; document tradeoffs and any unavailable measurements honestly.

## Out of Scope

- The Rust model-execution port, model packaging/rights decision, persistent embedding protocol and possible shared-memory ring buffer, and a binary split between indexing and search are deferred as **candidates**, not promised features, in the 0.3.3 pre-spec.
- Imported-source search optimization and refresh state-machine extractions are not 0.3.2 implementation work. Optional imported-source search profiling is not a release gate. Imported-source refresh is not parallelized here.
- Worktree mapping and ranking refactors, refactoring solely to satisfy soft metrics, external-command migration, model re-embedding, silent service startup and implicit model downloads are not part of this release.
- Separate Semgrep memory profiling, new OS-level process-memory enforcement, and exhaustive cross-architecture tuning are not required. Peak memory of the **whole refresh tree** remains part of release evidence.
- This spec does not retroactively complete the superseded #83/#84 benchmarks or undo the explicit v0.3.1 waiver.
