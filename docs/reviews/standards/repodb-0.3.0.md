## Sub-review 4 — State, data flow, and persistence

- **Review-criteria quality: PASS** (the post-release criteria clearly require authoritative state ownership, transactional/atomic persistence, and preservation of prior usable state after failure).
- **Release conformance: FAIL** for preservation of published source metadata on failed import refresh; other areas are mixed/partially verified as noted below.
- **Evidence scope:** v0.3.0 tag resolves to `f7cc6bc5451204c5696f1bbef7e5575772820f47` (HEAD). Inspected `src/imports.rs` refresh staging and publication paths, `src/imports/sources.rs` schema initialization, `src/history.rs` staging/publication transaction, `src/main.rs` refresh orchestration, and relevant CLI tests. RepoDB search was attempted (`repodb search 'state persistence database write'`) but unavailable because the checkout reported “no embeddings; run refresh”; no refresh was performed. This is source review, not a runtime test run.
- **Flow and ownership:** import refresh reads registered sources, validates/transforms content and embeddings into SQLite TEMP staging tables, validates dimensions, then publishes staged imports (and history, for full refresh) inside `history::publish_transaction`, an IMMEDIATE transaction guarded by a data-version snapshot (`src/main.rs` refresh branch around lines 2027–2050; `src/history.rs:875–882`; `src/imports.rs` `refresh_with_size_limit` / `publish`). Persistent imported versions, units, and git units are replaced transactionally. PDF conversion cache writes use a unique temp file, sync, then rename (`src/imports/cache.rs:131–165`); cache is documented in code as an optimization, while converted PDF representation is stored in the DB.
- **Finding S-92-1 — failed refresh mutates durable source metadata (medium):** During staging, unresolved Git pins are written directly to `imported_sources` (`src/imports.rs`, inside `refresh_with_size_limit`, `UPDATE imported_sources SET requested_revision...pinned_commit...`); URL source errors also write stale fetch status/error/attempt time directly to `imported_sources` before returning an error (`src/imports.rs`, `source_result` error branch). These writes occur before `publish_transaction`, and therefore are not part of its rollback boundary. A later error (e.g. a subsequent source failing) can leave persistent source metadata changed even though staged content was not published. This conflicts with the criteria that failed operations preserve prior usable state / do not publish a partial logical result unless documented. Existing tests explicitly check preservation of published imports/history for failed imports-only refresh (`tests/cli.rs` around 2027+) but do not establish rollback of these metadata changes. **Acceptance:** stage all durable source metadata changes and apply them only in the publication transaction, or explicitly define the metadata as independent attempt-state; add failure-injection coverage asserting intended metadata behavior alongside unchanged published content.
- **Other boundaries:** `init(c)` performs schema creation/migrations before refresh staging and also inside `publish`; publication transaction contains the later migration and wholesale row replacement. `sources::init` adds columns/backfills checksums and rebuilds legacy tables (`src/imports/sources.rs:init`); this is useful schema adaptation but migration behavior under interruption/failure was not fully tested here. No conclusion is made that SQLite DDL is non-atomic; migration transaction ownership depends on call context.
- **Coverage/evidence:** CLI coverage includes persistence across failed import refresh, dimension mismatch, retention, and legacy migration scenarios (`tests/cli.rs` around lines 2027–2055, 2324+, and 2391+; `src/imports/sources.rs` migration unit tests). Tests were inspected but not executed. Cancellation/interruption recovery, concurrent writer races for import refresh, and crash durability were not dynamically validated.
- **Residual risks / unknowns:** external Git mirror clone/fetch and PDF cache are filesystem side effects outside SQLite rollback; the cache is treated as disposable, while mirror lifecycle/cleanup and interruption behavior were not established by this scoped review. Full supported-platform, crash-recovery, and repeated-operation testing was not run. No claim of passing tests or release readiness.
