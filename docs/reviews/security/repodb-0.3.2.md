### Failure recovery
- [ ] Status: In progress
- Scope / owner: Parser crash/timeout/retry, cancellation/deadline, database writes, migrations, process cleanup and prior-snapshot preservation / owner TBD.
- Evidence: The exact target full suite passed (command and environment above). Target tests cover failed refresh/index preservation, parser retry then fallback, cancellation/deadline abort, worker subprocess timeout, oversized outputs, publication transaction failures, failed migration retry, corruption fail-closed behavior, and cross-file-descriptor writer locks.
- Findings / rationale: **P1 / Medium recovery-contract finding:** scoped refresh can commit after the total refresh deadline has expired, then the caller reports failure. At target `src/history.rs:3878-3916`, `refresh_scoped` begins an IMMEDIATE publication transaction, copies staged rows, and calls `tx.commit()` without a deadline check; `src/commands/refresh.rs:94-109` checks the deadline only after `refresh_update_excluding`/`refresh_changed_excluding` returns. I reproduced with a fresh tiny Git repo/database: initialize, create one additional commit, hold `BEGIN IMMEDIATE` from a second SQLite connection for 1.6 seconds, then run `refresh --update <commit>` with `REPODB_MAX_REFRESH_DURATION_SECS=1`. All 3/3 trials returned exit 2 with `refresh exceeded its total wall-clock deadline` while the new commit was present in `git_commits`. Reproducer: `/tmp/repodb-security-0.3.2-deadline-publication-repro.py`; binary was built from exact target source. This is not a partial/corrupt snapshot, but violates the specified abort/rollback behavior and means a failed command has committed. Acceptance: check the deadline after the lock is acquired and immediately before publication commit; add a deterministic regression injecting delay/lock at publication and assert expired operations leave prior state intact (or revise/document cancellation semantics if commit completion is intentionally non-cancellable). SIGKILL/power-loss at every publication boundary and platform-specific filesystem durability are also unverified. Corrupted databases are rejected rather than automatically repaired.
