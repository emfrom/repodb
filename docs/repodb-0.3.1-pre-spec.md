# RepoDB 0.3.1 — embedding and parsing throughput pre-spec

Status: **proposal for review, not approved implementation or a release gate**. This follows the 0.3.0 spec; it does not change #83's benchmark protocol or claim that #83/#84 are complete. No dependency, distribution, or model-license choice is approved by this document.

## Problem and measured starting point

Native Git history refresh stages units in batches of up to 256 and overlaps a single embedding worker with segmentation. When the configured executable resolves to `~/bin/generate_embeddings`, Rust starts `generate_embeddings --json -0 -` for each batch, pipes NUL-separated texts into stdin, consumes one JSON vector per line, then closes/waits. The CLI connects to a persistent local Python model daemon, which encodes up to 512 texts per request (model batch size 128). Other configured commands fall back to per-unit invocation; imported sources currently embed one unit per process. The current CLI flushes a partial `-0` batch only on EOF: retaining its process and leaving stdin open after 256 texts would deadlock without a new batch framing protocol.

On pinned, clean RepoDB `13639d6` and ProtonSync TypeScript `7c77aab`, using the pinned 0.3.0 candidate binary and **direct** built-in embedder (no logging wrapper), sequential fresh `init` took 152.59 s (255 MiB peak RSS; 46,049 indexed units) and 42.92 s (157 MiB; 18,926 units), respectively. Both resulting databases reported semantic readiness. These were not cold-cache trials. In a separate warmed-daemon microbenchmark (256 source-derived 450-character slices, six alternating paired trials), a new CLI process took median 451 ms, while direct socket requests took 336 ms: median paired difference 115 ms per batch. Twelve empty CLI invocations took median 83.5 ms. These are **not** measured end-to-end savings: the socket path also differs in serialization and output formatting. Minimum batch counts implied by those unit counts are about 180 and 74; multiplying by 115 ms suggests approximately 21 s and 9 s of *potential* overhead, not a release promise. Raw scratch measurements: `/tmp/issue83-cli-measurement.json` (not a reproducible release artifact).

## Proposed outcome

1. Remove avoidable short-lived CLI process startup per embedding batch, with an explicit batch API for both native history and imports; do not make embedding behavior depend on an executable's home-directory path. **Decide first** whether Rust model execution belongs inside this project (in-process, a workspace crate, or a bundled binary) or remains a separately maintained component with a stable protocol. Preserve a configurable external embedding command as a supported compatibility/privacy boundary unless an explicit migration decision changes that contract. Avoid a silently running long-lived service; if one is necessary for model performance, specify its lifecycle and observability separately.
2. Evaluate a Rust port of **model execution**, not just a Rust socket client for the Python daemon. A client alone does **not** meet the Rust-port goal. Choose and document a Rust inference runtime, model artifact format, tokenizer/pooling/normalization implementation, version pins, offline model lookup, packaging and license/redistribution terms **after** a primary-source compatibility and rights review. No implicit download at query or refresh time. Do not add dependencies or bundle model weights before that decision.
3. Keep semantic behavior explicit: `all-MiniLM-L6-v2` must produce finite, nonempty 384-dimensional vectors for normal, empty/whitespace and Unicode units; reject wrong dimensions, invalid values, partial batches and model identity mismatches. Specify a numerical tolerance using a pinned text-vector comparison against the existing model, and assess retrieval/ranking drift rather than claiming bitwise equivalence across runtimes. Existing indexes must retain an unambiguous model identity; re-embedding/migration must be explicit and reversible, never silently mix vector spaces.
4. Bound concurrent preparation, batch input/output bytes, model memory, and DB writes. Preserve ordered unit-to-vector association, source anchors, current failure atomicity and SQLite's single-writer constraints. On failure, surface actionable errors and leave the previous usable index intact. Respect existing configured-command privacy disclosures; document where model artifacts and text are processed and stored.
5. Parse independent source blobs with bounded parallel Semgrep processes. Determine the default worker count **at runtime** as `max(1, floor(available_parallelism / 2))`, using the logical parallelism available to this process, rather than a fixed machine-specific cap; allow a positive user-configured override. This is a portable heuristic, not a claim to detect physical cores: simultaneous multithreading, CPU quotas/affinity, and mixed-performance cores differ by host. Keep the pending-task queue and captured output memory bounded; preserve deterministic source/unit ordering, current timeout and fallback behavior, and single-writer database semantics. Coordinate parsing with embedding so the two stages do not oversubscribe memory or processors without measurement.

## Architectural decisions before implementation

- **Embedder ownership and boundary:** compare integrating Rust inference into RepoDB against maintaining it as a separate installable component. Evaluate portability, GPU/CPU support, model-artifact distribution, optional dependencies, startup and steady-state throughput, memory, failure isolation, and compatibility with external commands. Record the chosen ownership, API/protocol, versioning and upgrade path in the final spec; do not treat this pre-spec's Rust-port goal as a decision to merge the embedder into the main binary.
- **Database input/output boundary:** decide whether to split the current executable into an input/index-building side (source discovery, parsing, embedding, schema migration and writes) and an output/search side (reads, ranking and presentation). Compare one binary with internal modules/subcommands, separate binaries over a shared database contract, and other viable boundaries; a split is not predetermined. Specify who owns schema migrations and write locks, how readers behave during refresh or partial failure, which side loads the model, shared data types and schema/version compatibility, installation footprint and CLI backward compatibility. Keep SQLite's atomic publication and existing read/search semantics across any chosen boundary.
- Record these as explicit architectural decisions with measured tradeoffs **before** implementation tickets or the final 0.3.1 spec; do not infer a binary split from the Semgrep or embedder microbenchmarks alone.

## Semgrep concurrency evidence

An isolated three-trial test parsed the same 24 pinned RepoDB Rust and 15 pinned ProtonSync TypeScript tracked files using `semgrep-core -l LANGUAGE -json -full_token_info -dump_ast FILE`, including process startup, output capture and JSON decoding. Median wall time was 6.81 s at 1 worker, 3.81 s at 2, 2.26 s at 4, 2.05 s at 8 and 2.16 s at 16 (`nproc` on the test host). This supports bounded parallelism greater than one, **not** a hard-coded limit of eight or an end-to-end speedup claim. It samples HEAD files rather than all historical blobs and does not run concurrently with RepoDB embedding and SQLite writes. Scratch measurements: `/tmp/issue83-semgrep-parallel.json` (not a release artifact).

## Verification before adoption

- Resolve the embedder ownership and database input/output boundary above, then decide runtime/model-format/license feasibility, target platforms, CPU/GPU behavior, installation and uninstall plan. Prototype a small batch without changing the shipped default; compare the same pinned vectors and semantic top-k results to the present executable. Test whitespace, Unicode, batch edges, crash/error recovery, resource limits, repeated refresh, imported sources, offline operation and existing external-command compatibility.
- Benchmark actual **fresh** and repeat refreshes on pinned RepoDB and ProtonSync corpora with the same cache conditions and model, reporting wall time, peak RSS, bytes, accuracy and latency. Record both old and new paths, confidence/variance across repeats, and any model or artifact differences. Do not infer full-run speedup solely from the microbenchmark. Set acceptance thresholds from those runs before calling this release-ready.
- Test Semgrep serial versus runtime-default and overridden worker counts during a full refresh on constrained, SMT and heterogeneous hosts where available. Check peak concurrent processes, RSS, parser fallback/timeout behavior, result determinism, and contention with embedding. Adjust the heuristic if full-run evidence warrants it; do not make the measured eight-worker test-host optimum a portable constant.
- Keep the 0.3.0 release evidence and ticket decisions independent: no #83/#84 closure or threshold change follows from this proposal. Follow-up implementation tickets and final 0.3.1 spec require explicit review.

## Open decisions

Which Rust inference runtime and artifact source are legally and operationally supportable? How will CPU/GPU selection and offline installs work on supported targets? Should embedding move into this project at all, and should input/indexing and output/search remain in one executable or be separated at the database boundary? What numerical and retrieval tolerance is acceptable? How should old indexes and external embedding commands coexist? Is a persistent inference worker warranted by measured load time, or is in-process inference enough?
