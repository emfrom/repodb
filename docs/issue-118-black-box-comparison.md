# Issue #118 — v0.2.2 / v0.3.0 black-box search comparison

This is black-box CLI evidence from the exact release commits, not an implementation comparison. Sources were `/tmp/repodb-022` (`v0.2.2`, `12c470004f42b1184a3e4f8a911018c93200d463`) and `/tmp/repodb-030` (`v0.3.0`, `f7cc6bc5451204c5696f1bbef7e5575772820f47`); both checkouts were clean. Binaries are `/tmp/repodb-target-022/release/repodb` and `/tmp/repodb-target-030/release/repodb`. Their pinned source builds were verified with `(cd /tmp/repodb-022 && CARGO_TARGET_DIR=/tmp/repodb-target-022 cargo build --release --locked)` and the corresponding `repodb-030` command; both reported `Finished`/up-to-date. The current toolchain was stable `rustc 1.99.0 (b940084d7 2026-09-28)`, `cargo 1.99.0 (5f94df478 2026-08-27)`. v0.3.0 prints `repodb 0.3.0`; v0.2.2 rejects `--version` as an unknown command (exit 2).

## Reproduce

Run `XDG_CONFIG_HOME=/home/emfrom/etc benchmarks/issue-118/repro.sh` (or set the environment to an equivalent config). The committed script creates a unique two-commit local Git fixture with fixed dates/text, initializes independent databases, and captures 16 commands with exit status, stdout, and stderr in separate files. It prints the unique output directory; this run's manifest and raw files are in `/tmp/issue118-repro.0CW862/outputs/`. The fixture HEAD was `13e7a8a7bfa5cd0eba2b1ddabf388c14544c192d`. Both database records show the same configured embedder command `/home/emfrom/bin/generate_embeddings`, model `all-MiniLM-L6-v2`, dimension `384`; `XDG_CONFIG_HOME` and `HOME` are recorded in the manifest. This means semantic results were available, and default combined-search observations are model/config-specific.

Both versions use the same fixture, `amber-needle` query and isolated database paths. The v0.2.2 default search returned one grouped current-file result (`notes.txt`, lines 1–3) with `path`, `line_start`, `line_end`, `text`, `commit_id`, and `blob_id`; its no-match query returned `[]`. The v0.2.2 CLI rejected `--exact` as unexpected (exit 2), so explicit exact-mode behavior is not an apples-to-apples option comparison. v0.3.0 exact mode returned three matching results as a bare array. A v0.3.0 `--history=all` query returned a paginated object with `cursor`, `results`, `snapshot_id`, `total_count`, and `truncated`. Complete ordinary results can be a bare array; paginated responses use the object shape.

## Observations and migration implications

- **Result selection/ordering:** v0.2.2's default query produced a single current-file grouped result, not individual matching lines. In this v0.3.0 run, default combined JSON was ordered `commit_message`, `content` (`notes.txt`), `diff` (`added`), `diff` (`removed`); explicit exact JSON was `content`, added diff, removed diff. The no-match default query produced the same four semantic candidates in the same observed order, while exact no-match was empty. These are fixture/model observations, not universal ordering guarantees. Thus the default outputs are materially different and should not be treated as equivalent result lists or orderings. These differences align with the intentional v0.3.0 `--type=all`/combined contract and bounded-pagination rules in `docs/repodb-0.3.0-spec.md`, “Search interface, ranking and output”; this comparison does not establish a non-regression claim or an exact v0.2.2-to-v0.3.0 option mapping. Use explicit v0.3.0 matching options when migrating a caller with a known matching expectation and verify the resulting evidence shape.
- **JSON:** observed v0.2.2 output is a results array with the fields above. v0.3.0 adds richer evidence/result fields (including component, match/ranking metadata and reference identifiers); complete ordinary results can still be a bare array, while paginated responses wrap the array with snapshot/pagination metadata. Consumers must not assume all v0.3.0 JSON is an array.
- **Pagination:** the v0.2.2 attempt `search amber-needle --limit 2 --json` exited 2 with `repodb: unexpected argument --limit`. This binary exposes no `--limit` pagination option in the tested CLI; no claim is made about other v0.2.2 pagination mechanisms. The same v0.3.0 command succeeded and returned two results plus a cursor, snapshot id, `truncated: true`, and `total_count: 3`.
- **Errors and exit status:** both reject `--not-an-option` on search with exit 2 and stderr `repodb: unexpected argument --not-an-option`. The v0.2.2 `--version` attempt exits 2 with `repodb: unknown command: --version`; v0.3.0 prints `repodb 0.3.0` and exits 0. The v0.3.0 default no-match query returned four semantic candidates in this configured-model run; the explicit exact-mode no-match query returned `[]`. This is an observed consequence of default combined search, not an exact-search result.

## Validation limits

Default v0.3.0 combined-search outputs depend on the configured embedding model and are preserved as observations, not general ordering guarantees. The fixture is deliberately small: one file, two commits, repeated query term, no-match, option error and one pagination boundary. It does not establish performance, every JSON field, all error cases, or all migration behavior. The capture records the observed model/config so a rerun can identify whether its environment matches.
